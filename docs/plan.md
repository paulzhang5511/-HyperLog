## 1. Overview

把 `docs/spec.md` 拆解为 **20 个可独立验证的任务**，分 7 个阶段推进。每个阶段结束都是一个**可运行、可手工验证的二进制**——不是"底层全做完再接线"，而是每完成一片垂直切片，用户就能打开窗口真实地用一次。

交付节奏：

| 阶段 | 结束后用户能做的事 |
| --- | --- |
| Phase 0 | 打开一个空白窗口 |
| Phase 1 | （无 UI 变化）核心索引逻辑跑通并被单测证明 |
| Phase 2 | 打开 1~3 个日志文件并流畅滚动浏览 |
| Phase 3 | 看到按级别着色的日志 |
| Phase 4 | 边搜边出结果，有进度条，可随时停止 |
| Phase 5 | 把检索结果导出成文件 |
| Phase 6 | 性能达标、空闲不烧 CPU、文档齐全 |

## 2. Architecture Decisions（决策与理由）

| # | 决策 | 理由 | 对应 Spec |
| --- | --- | --- | --- |
| A1 | `src/core/**` 与 `src/ui/**` 严格分层，core 禁止引用 egui | 索引/检索/高亮都能脱离 GUI 单测，否则只能靠肉眼看窗口 | §6 |
| A2 | `FileSet` 统一全局行寻址：`global_idx → (file_idx, line_idx)` | 修复 PRD 只能渲染第一个文件的缺陷（D1），且是检索结果渲染的公共底座 | §7.2 |
| A3 | `SearchHit` 只存 `(u32, u32)` 坐标，不存文本 | 500 万命中从 ~500 MB 降到 40 MB；渲染惰性取行、导出流式取字节 | §7.3 / D8 |
| A4 | 后台任务用 `std::thread::spawn` + 内部 `rayon` 分块，不用 `rayon::spawn` 直接跑全量 | 只有在自己起的线程里才能按块推进、按块发进度、按块检查取消 | §7.4 |
| A5 | 分块单位用**字节**（目标 8 MiB，边界对齐到行） | 按行数分块会因行长差异导致块耗时抖动、进度条忽快忽慢（D5） | §7.4 |
| A6 | 计数用块内本地累加 + 块末汇总，禁止逐行 `fetch_add` | 逐行原子自增在多核下伪共享，实测会显著拖慢热路径（D7） | §7.4 |
| A7 | 高亮复用检索时编译的同一个 `Regex` | 否则"正则命中"与"字面量高亮"语义不一致，用户看到高亮位置跟命中对不上（G5） | §7.6 |
| A8 | 高亮**只对可视区（~60 行）执行** | 10 M 行全量高亮会拖垮帧时间；视口外不计算 | §7.6 / P4 |
| A9 | 单行渲染超过 100,000 字符时截断为 `"…(行过长已截断)"` | 单行 1 MB 日志会让 egui 的字形布局耗时爆炸（ms 级 → 秒级） | §11.3 fixtures `long_line.log` |
| A10 | 空闲时（无后台任务）不 `request_repaint` | 否则 egui 会持续满帧重绘，空转 CPU（P12 要求 < 2%） | §8.4 |
| A11 | `SearchMessage::Partial` 每块推送，且 UI 侧发送**节流（≥100 ms）+ 每帧 drain 上限 1000 条** | 边搜边出结果；同时防止小块打满 channel 与消息洪水饿死渲染（D4/D6） | §7.4 / §8.4 |
| A12 | 取消用 `Arc<AtomicBool>` 轮询，不用 `channel` 终止 | 无锁、无内存分配、可在 rayon 闭包内零成本检查（G1） | §7.4 |
| A13 | 依赖版本以 PRD 为基线，实现时用 `cargo add` 校验并回写 spec §4 | 本环境无法访问 crates.io 查询，必须在实际执行时确认 | §3 假设 9 |

### 2.1 待定（不阻塞开工，实现中再定）

| 项 | 现状 | 决策时机 |
| --- | --- | --- |
| 索引偏移用 `usize`(8 B) 还是按文件体积自适应 `u32`(4 B) | 先用 `usize`（简单、正确） | T19 性能实测后，若 P3 不达标则对 <4 GiB 文件改用 `u32` |
| 折行开启时的行高估算 | 先固定行高（折行时可能滚动位置略偏） | T08 实现时评估复杂度，偏差可接受就留到 M5 之后 |

## 4. Vertical Slices（垂直切片，而非水平分层）

**不做**：先写完所有 core，再写所有 UI，最后接线。
**要做**：每片切片都打通 `core → app 状态 → UI`，阶段结束即可手工验证。

| 切片 | 打通路径 | 结束时的可验证行为 |
| --- | --- | --- |
| S1 | `rfd 对话框 → LogFileIndex → app.files → ScrollArea` | 打开 3 个文件，从头滚到尾，无空白行 |
| S2 | `LogFileIndex → highlight::segments → 彩色 Label` | ERROR 红、WARN 黄，`errors=3` 不着色 |
| S3 | `UI 输入 → SearchEngine 后台线程 → channel → app.results → 结果视图` | 边搜边出结果，进度条平滑，可随时停止 |
| S4 | `app.results → core::export → BufWriter → 磁盘` | 导出文件与源文件命中行逐字节一致 |

## 7. Risks and Mitigations

| # | 风险 | 影响 | 概率 | 缓解策略 | 触发时机 |
| --- | --- | --- | --- | --- | --- |
| R1 | `egui`/`eframe` 0.36.1 版本不存在或 API 与 PRD 示例不符（`show_rows`、`ScrollArea` 签名变化） | 高 | 中 | T01 就做编译冒烟；若版本不可用，改用 `cargo add` 解析到的最新稳定版并**回写 spec §4**；API 差异在 T07 前摸清 | T01 |
| R2 | 索引内存超标：1 亿行 × 8 B = 800 MB，可能顶不住 P3 | 中 | 中 | 对 <4 GiB 文件改用 `Vec<u32>` 存偏移（4 B/行，减半）；仍不够则分块索引+惰性加载 | T19 |
| R3 | 超长单行（1 MB+）导致 egui 字形布局卡死 | 高 | 中 | A9：渲染时截断到 100,000 字符并加提示；T08 实现并用 `long_line.log` 验证 | T08 |
| R4 | 高亮计算拖慢滚动帧率 | 中 | 中 | A8：仅对可视区约 60 行执行；`level_re`/`hit_re` 复用编译结果，绝不每行重建 | T10 |
| R5 | 正则病态表达式吃满内存/CPU | 中 | 低 | `RegexBuilder` 设 `size_limit(16 MiB)` / `dfa_size_limit(8 MiB)`；编译失败走内联错误 | T12 |
| R6 | 后台线程洪水打爆 channel 或饿死渲染 | 中 | 中 | A11：发送端 ≥100 ms 节流，接收端每帧 drain ≤1000 条 | T12 / T18 |
| R7 | `unsafe` 的 mmap 在文件被外部 truncate 时 SIGBUS（macOS） | 高 | 低 | MVP 不处理，在状态栏提示"文件已被修改请重新加载"；写入 spec §13 已知限制 | T04 |
| R8 | Windows 上 mmap 锁定文件，其他进程无法删除/覆写 | 中 | 中 | MVP 接受并在 README 说明；若反馈强烈，后续加"只读快照"降级方案 | T04 |
| R9 | 多文件加载的内存叠加（32 × 16 GiB 理论上可行但不可控） | 中 | 低 | 加载时校验累计体积上限（spec §3 假设 5 补：累计 ≤ 32 GiB），超限拒绝并提示 | T06 |
| R10 | 折行模式下的行高估算不准，滚动位置漂移 | 低 | 中 | 折行先按固定行高实现（T08），偏差明显则 M5 之后改为动态测量 | T08 |
| R11 | `rayon` 全局线程池与 egui 主线程争抢核 | 低 | 低 | 限制 rayon 线程数为 `num_cpus - 1`（≥1），保证 UI 有核可用 | T13 |

## 8. Parallelization Opportunities

**可安全并行**（无共享文件、契约已定）：

| 组合 | 前提 |
| --- | --- |
| T03（fixtures/CI） ∥ T02（窗口骨架） | T01 完成 |
| T09（highlight 纯函数） ∥ T06–T08（浏览 UI） | 无交集文件 |
| T12–T14（检索引擎） ∥ T15（检索 UI） | **必须先完成 T11 契约定义** |

**必须串行**：

- T04 → T05 → T06 → T07：索引 → 寻址 → 打开 → 渲染，硬依赖链
- T11 → T12 → T13 → T14：契约 → 单线程跑通 → 并行化 → 加取消，逐步加复杂度（先对后快）
- T16 → T17：引擎 → UI

**需协调**：T15（UI）与 T12–T14（引擎）共享 `SearchMessage` 契约，T11 必须先落地且双方都不得单方面修改。
